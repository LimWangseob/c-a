## 0. 왜 이 문서인가 (D8 2·3단계 설계와의 관계)

`DOMAIN_D8_SETTLEMENT_PHASE23.md`는 정산을 **"단계(1·2·3) + 흡수(계약·사업·채권자)"** 축으로 조직했다.
2026-10-05 소유자는 정산을 **"3층(누가 누구에게 지급하는가)"** 축으로 다시 정의했다. 두 축은 **직교·상보**다:

- 단계 축(D8) = **구현 순서**(오프라인 계산 → 라이브 수집 → 계약 대비). "언제 짓는가".
- 층 축(이 문서) = **지급 주체→수취 주체의 흐름**(플랫폼→판매자→위탁자 / 회사→채권자). "무엇을 계산하는가".

**중복 금지 규약**: 이 문서는 층의 **정의·경계·입출력 흐름·멀티플랫폼 정규화**만 쓴다. 각 층의 **수집 방법·파서·
원장 열·안전 규약·골든 확장**은 하위 문서에 있고 여기서 재서술하지 않고 **참조**한다. 하위 문서의 모듈 제안
(`settlement.py`·`contract_store`·`creditor_store` 등)은 이 문서의 층에 **그대로 배속**되며 새로 만들지 않는다
(§7에서 층↔모듈 매핑). 이 문서가 추가하는 **신규 설계 요소는 딱 둘**: (가) 3층 프레이밍과 층간 입력 관계,
(나) 멀티플랫폼 정규화(쿠팡+스마트스토어 ①의 합산·공통 스키마).

## 1. 3층 개요 · 정의 · 그림 · 용어

### 1.1 한 장 그림 (텍스트)

```
    [플랫폼]                      [커머스 판로(회사)]                  [채권자 ~370명]
  쿠팡 / 스마트스토어
        │ ① 플랫폼 정산                      │ ② 계약 정산                    │ ③ 채권자 정산
        │ (플랫폼 → 위탁계정/판매자)          │ (회사 ↔ 위탁자[계약자])         │ (회사 → 채권자)
        ▼                                    ▼                               ▼
  ┌─────────────┐    실지급 누적    ┌──────────────┐  회사 수익 몫   ┌──────────────┐
  │ ① 수집 원장 │ ───(입력)──────▶ │ ② 계약 정산  │ ──(입력)─────▶ │ ③ 채권자 원장│
  │ 플랫폼·계정 │                  │ 수익 배분식  │                │ 상환 배분    │
  │ ·기간·항목  │                  │ 달성률·잔액  │                │ (법률→소유자)│
  └─────────────┘                  └──────────────┘                └──────────────┘
   배치 수집(플랫폼별)              계산(① 합산을 입력)             계산·기록·감사만
```

### 1.2 층 정의 (지급 주체 → 수취 주체)

| 층 | 이름 | 지급 주체 → 수취 주체 | 한 줄 | 성격 |
|---|---|---|---|---|
| **①** | **플랫폼 정산** | 플랫폼(쿠팡·스마트스토어) → **위탁계정/판매자** | 위탁계정이 플랫폼에서 **실제 정산받는 금액**을 배치로 당겨와 계산·검증 | 수집(읽기)+계산 |
| **②** | **계약 정산** | 커머스 판로(회사) ↔ **위탁자(계약자)** | 계약서 기준 **수익 배분·달성률**을 ①을 입력으로 계산 | 계산(오프라인)+원장 |
| **③** | **채권자 정산** | 회사 → **채권자(약 370명)** | 회사 수익에서 상환 배분. 기준은 **법률 검토 후 소유자**, 앱은 **계산·기록·감사만** | 원장(법률 민감) |

- ①은 **플랫폼별로** 들어온다(쿠팡·스마트스토어가 각각 다른 규칙·자료). ②는 한 위탁자가 여러 플랫폼에 걸칠 수 있어
  **플랫폼 합산 기준**으로 계산될 수 있다(§5). ③은 회사 전체 수익(②의 회사 몫 누적)에서 배분한다.
- **멀티플랫폼은 ①에서만 발생**한다(②③은 회사 기준 단일). 그래서 정규화 부담은 ① 안에 가둔다(§5).

## 2. 층간 관계 · 데이터 흐름 (어느 값이 어느 층의 입력인가)

### 2.1 흐름 (확정 방향 · 금액 구현식은 하위 문서)

```
① 플랫폼 정산 수집(배치·플랫폼별)
   ├─ 쿠팡:      WING 세션 수집(collector 확장/엑셀 폴백) → 실지급·지급일·확정상태   [상세=D8 §2]
   └─ 스마트스토어: 네이버 커머스/정산 자료(형식 미확인·§8 G4)                        [미결]
        │  산출(①의 출력) = 플랫폼 정산 레코드(플랫폼·계정·기간·항목·실지급액·지급일·확정상태)
        │  (계산·검증: payout 지급일 / settlement_amount 금액식 / settlement_parse 불변식)  [상세=SETTLEMENT_MODULE §2~6]
        ▼
② 계약 정산 계산
        입력 = (①의 실지급 누적, 플랫폼 합산) + (계약 조건 = 계약 원장) + (관리 기간)
        산출 = 계약별/계정별 **수익 배분·달성률·잔액·예상 달성일 + 회사 수익 몫**   [상세=D8 §3·SETTLEMENT_MODULE §7]
        ▼
③ 채권자 정산 배분
        입력 = ②의 **회사 수익 몫 누적**(회사 전체)
        산출 = 채권자별 상환 배분(규칙=법률→소유자) → 채권 원장에 기록        [상세=D8 §4.3]
```

### 2.2 입력 책임표 (어느 값이 어느 층의 입력인지 — 이 문서의 핵심 확정)

| 값 | 생산 층 | 소비 층 | 비고 |
|---|---|---|---|
| 실지급액·지급일·확정상태(플랫폼별) | ① | ② | ①의 출력 = 플랫폼 정산 레코드(§3.1) |
| 플랫폼 합산 실지급 누적 | ① 정규화(§5) | ② | 한 위탁자의 쿠팡+스마트스토어 합 |
| 계약 조건(수익식·계약금·약정이익금·비용부담) | 계약 원장(②의 저장소) | ② | IO 11-3·`contract_store` |
| 관리 기간(계정·상품이 관리중이던 구간) | 셀독등록원장(`registry_history.managed_between`) | ② | 과거 계정 포함 |
| **회사 수익 몫 누적** | ② | ③ | ②가 수익 배분식으로 산출한 회사 몫 |
| 상환 배분 규칙 | **소유자(법률 검토)** | ③ | 앱은 하드코딩 금지·입력/설정으로 받음 |
| 채권 확정·상환 기록 | 사람(화면·수동) | ③ | append·정정=반대기록 |

- **단방향**: ①→②→③. 역방향 흐름 없음(채권자 정산이 플랫폼 정산을 바꾸지 않음). 감사·되돌림은 각 층 원장 안에서.
- **계산값 vs 실지급**: ①의 payout/settlement_amount 계산은 **예측**(`is_estimate=True`), **실지급은 수집 파일/API 값이 정본**
  (SETTLEMENT_MODULE §3). ②·③은 **정본(확정분)**을 입력으로 쓴다(예측값으로 상환 배분 금지 — R1).

## 3. 각 층 데이터 모델

> 열·필드 상세는 하위 문서가 SSOT. 여기서는 **층 경계에 필요한 최소 스키마와 성격**만 확정한다.

### 3.1 ① 플랫폼 정산 — 수집 원장 (플랫폼·계정·기간·항목)
- **성격**: 읽기 전용 수집(쓰기 도메인 아님·쓰기 안전 규약 비해당, D8 §2). 플랫폼이 준 값을 그대로 적재 + 계산 검증.
- **공통 스키마(이 문서 확정·정규화 §5)** — `PlatformSettlement`(제안):
  `플랫폼`(COUPANG/SMARTSTORE) · `계정` · `채널`(쿠팡 MARKETPLACE/ROCKET_GROWTH 등) · `기간`(정산 주/월) ·
  `항목`(매출·쿠폰·수수료·부가차감…) · `실지급액` · `지급일` · `확정상태`(확정/미확정) · `is_estimate` · `_raw` 참조.
- **쿠팡 세부**(확정분 = SETTLEMENT_MODULE §4·COUPANG_SETTLEMENT_DOMAIN §3~4): 윙 E=A−B−C−D·최종=E−F /
  로켓그로스 실지급 = 정산대상액−밀크런−광고비−CFS / 지급일 6종 POLICY. **쿠팡 스키마는 기구현**(1단계).
- **스마트스토어 세부**: **미확인**(§8 G4). 정규화 어댑터로 공통 스키마에 사상(§5).

### 3.2 ② 계약 정산 — 계약 원장 (D8 §4.1과 정합)
- **저장소 = 계약 원장**(`contract_store.py`·D8 §4.1·IO 11-3 13칸). **버전 이력**(계약 개정 = 새 이력 줄·`as_of`)·
  유효/만료 = 이력 replay. registry 패턴 재사용(§7).
- **계산 = ② 정산 모듈**이 (계약 원장 + ① 실지급 누적 + 관리 기간)으로 달성률·잔액·예상 달성일·**회사 수익 몫** 산출.
- **원장 책임 분리(확정·D8 §4.1)**: 수수료·약정이익금 열은 **셀독등록원장이 아니라 계약 원장**에. 중복 저장 금지.
- ⚠ 계약 조건 스키마(수익 계산식 표현)는 **실제 계약서 수령 후 확정**(§8 G3·D8 §3.1). 지금은 입력 요구 목록.

### 3.3 ③ 채권자 정산 — 채권/상환 원장 (D8 §4.3·R2② 규칙)
- **성격**: 돈 원장 → **append-only·정정 = 반대 기록**(지우지 않음)·잔액 = 이력 replay(채권확정 − 상환 누적).
- **파일 분리(확정·R2②)**: **별도 스프레드시트**·공유 최소(소유자·대표·정산담당·서비스계정만).
- **권한·가림(확정)**: 이름·연락처·상환계좌 = 민감(가림)·원문은 대표/정산담당만(계좌는 대표만)·**열람 기록**(감사)·
  로그/결과/git/백업에 원문 금지·로컬 백업 제외 또는 가림본만. 상세 = D8 §4.3·IO 12-x.
- **배분 계산**: 규칙이 소유자/법률로 확정되면 그 규칙대로 **계산·기록·감사만**. **미확정 중엔 기록(채권확정·수동 상환)만**.

## 4. 1단계 payout 계산과 3층의 관계 (기구현 모듈 ↔ 층 매핑)

**결론(확정): 기구현 1단계(payout·settlement_amount·settlement_parse·holiday_kr)는 전부 층 ①에 속한다.** ②가 아니다.
①은 "위탁계정이 플랫폼에서 받는 금액"이고, 1단계 계산기가 바로 그 **지급일·금액·검증**을 계산하기 때문이다.

| 기구현 모듈(실측) | 공개 함수(실측) | 층 | 역할 |
|---|---|---|---|
| `payout.py` | `payout_date`·`payout_amount`·`estimate`·`week_sunday`·`PayoutEstimate` | **①** | 플랫폼 **지급일**(쿠팡 6종 POLICY)·예측 금액 |
| `settlement_amount.py` | `mp_revenue`·`rg_payout`·`rg_home_profit`(keyword-only) | **①** | 플랫폼 **정산 금액식**(윙 E·RG 실지급·RG 홈이익) |
| `settlement_parse.py` | `read_insights_xlsx`·`check_invariants`·`make_meta`·`parse_int/pct/id/date` | **①** | 판매분석 파싱·불변식(①의 데이터 품질 게이트·D9 통계에도 공급) |
| `holiday_kr.py`+`holiday_source.py` | `holidays`·`is_business_day`·`add_business_days`·`substitute_holidays` | **①** | 지급일 계산의 영업일 근거(쿠팡 지급일 규칙 전용) |
| `settlement.py`(신규·미구현) | `achievement(...)`(D8 §7) | **① 집계 + ② 계산** | 1단계 모듈 조립 퍼사드(① 집계) **및** 계약 대비 달성률(②) |

- `settlement.py`만 층을 **걸친다**: 정산건 집계 = ①, 계약 대비 달성률 = ②. 구현 시 두 책임을 함수로 분리한다
  (수집·파서·계산 혼합 금지·SETTLEMENT_MODULE §6 분해 지침). ②가 비대해지면 `settlement_contract.py`로 분리(§7).
- **쿠팡 지급일 규칙은 ① 안에서도 플랫폼 전용**: `payout.py`의 POLICY는 쿠팡 전용이다. 스마트스토어 지급일 규칙은
  다른 어댑터로 들어오고 payout.py를 오염시키지 않는다(§5·멀티플랫폼 분리).

## 5. 멀티플랫폼 정산 통합 (쿠팡 + 스마트스토어 ① 합산·정규화)

> 이 문서가 D8 대비 **새로 추가하는 핵심 설계**. D8은 쿠팡 전용이었다. v1은 쿠팡+스마트스토어.

### 5.1 어댑터 패턴 (제안)
- **플랫폼마다 수집·규칙이 다르다** → 플랫폼별 **어댑터**가 raw를 §3.1 공통 스키마(`PlatformSettlement`)로 사상한다.
  - **쿠팡 어댑터** = 기구현 재사용(collector 확장/엑셀 폴백 수집 → `settlement_amount`/`payout`으로 금액·지급일).
  - **스마트스토어 어댑터** = **미결**(네이버 커머스API/정산 자료 형식 수령 후·§8 G4). 지급일·수수료 규칙도 그때 확정.
- **정규화 = ① 안에만**. ②는 공통 스키마만 본다(플랫폼 분기 없음) → 플랫폼 추가 시 ②③ 코드 불변.
- **합산 기준(②로 넘길 때)**: 한 위탁자의 실지급을 **플랫폼 횡단 합산**(계정→위탁자/계약 매핑으로 묶음).
  주의: 플랫폼별 **기간·귀속 기준일이 다름**(쿠팡=구매확정/결제완료, 스마트스토어 미확인) → 합산 전 **기간 정규화 필요**
  (귀속 기준일 통일·미확인 구간 표시). 이 정규화 규칙은 스마트스토어 자료 확인 후 확정(미결).

### 5.2 선제 추상화 금지 (측정 기반)
- 지금은 플랫폼이 쿠팡 1개뿐 **실구현**(스마트스토어 미수령). **공통 스키마·어댑터는 스마트스토어 자료가 실제로 들어올 때**
  짓는다(전체 재작성 금지·측정 기반). 그 전에는 쿠팡 경로를 공통 스키마 **모양으로만** 유지(미래 어댑터가 끼도록).
- 근거: registry 공용 프레임을 "중복 측정 후"로 미룬 선례(D8 §4.0·R3)와 동일 규율.

## 7. 신규 모듈 제안 (층 배속 · D8 제안과 정합 · 중복 금지)

> D8 §6이 이미 제안한 모듈은 **그대로** 쓰고 층에 배속만 한다. 이 문서가 **추가 제안하는 신규 모듈은 2개**(★).

| 모듈 | 책임(단일) | 층 | 출처·재사용 |
|---|---|---|---|
| `settlement.py` | 1단계 조립 퍼사드(①) + 계약 대비 달성률(②) | ①·② | D8 §6·기제안 |
| `settlement_collect.py` **또는** collector 확장 | 정산·매출·부가 리포트 수집(fetch) | ① | D8 §6·기제안(collector 프리미티브) |
| `settlement_report_parse.py` | 매출·판매수수료·부가 리포트 xlsx 파서 | ① | D8 §6·기제안(`settlement_parse` 헬퍼) |
| ★ `platform_settlement.py` (제안) | **플랫폼 어댑터 → 공통 `PlatformSettlement` 정규화·플랫폼 합산** | ① | 이 문서 §5·`collector`+쿠팡 기구현 위에 얇게 |
| `contract_store.py` | 계약 원장(버전 이력·`as_of`·유효/만료 replay) | ② 저장소 | D8 §6·기제안(`registry_history`·`registry_gsheet`) |
| ★ `settlement_contract.py` (제안·선택) | `settlement.py`의 ② 부분이 비대해지면 **계약 정산 계산만** 분리 | ② | 이 문서(단일 책임·분해 시) |
| `creditor_store.py` | 채권/상환 원장(금액 누적 replay·정정=반대기록·가림·열람 로그·별도 파일) | ③ 저장소 | D8 §6·기제안(`registry_core` replay 변형) |
| ★ `creditor_settlement.py` (제안) | **상환 배분 계산**(규칙 주입·원장과 분리·계산/기록/감사) | ③ 계산 | 이 문서(원장=기록 / 계산=별도, registry↔settlement 분리 선례) |
| `worklog_store.py` | 업무일지 append 원장(운영 기록) | D8 흡수(층 밖) | D8 §6·기제안 |

- **왜 `creditor_settlement`를 원장과 분리하나**: registry(기록)와 settlement(계산)를 나눈 선례(SETTLEMENT_MODULE §0)와 동일.
  배분 **규칙은 하드코딩 금지·주입**(소유자/법률 확정 시 설정·입력으로) → 계산 모듈이 규칙을 인자로 받아 순수 계산.
  **규칙 미확정 중에는 `creditor_store`(기록)만 구현하고 `creditor_settlement`는 보류**(R1).
- **`platform_settlement`도 선제 금지**: §5.2대로 스마트스토어 자료 수령 전엔 만들지 않는다(쿠팡 경로를 모양만 유지).
- **분해 지침**: 수집=fetch만·파서=파일→객체·계산=순수·정규화=사상만. greenfield = 병합 충돌 0(D8 §6).

## 8. 갭 · 리스크 · 미결

- **G1 WING 정산 API 미확인(①·최우선)**: settlement-histories가 WING 세션 쿠키로 호출되는지 등 — 전부 `[미확인]`.
  `diag_settlement_endpoints.py` 사무실 라이브 실측이 선행. 상세·목록 = D8 §2.3·§9 G1.
- **G2 부가 리포트 조인키 미확인(①)**: 밀크런·광고·CFS 조인키(이익 과대·함정 5). 상세 = D8 §9 G2.
- **G3 계약 조건 스키마 미확정(②)**: 수익 계산식 표현(자유식 vs 구조화 규칙). 실 계약서 수령 후 확정. 상세 = D8 §3.1·§9 G3.
- **★G4 스마트스토어 정산 자료 형식 미확인(①·멀티플랫폼)**: 수집 경로(네이버 커머스API/정산 자료)·컬럼 스키마·
  지급일/수수료 규칙·귀속 기준일 전부 **미확인**. 스마트스토어 어댑터(§5.1)·기간 정규화 규칙은 이 자료 수령 후 확정. **(이 문서 신규)**
- **★R1 채권자 법률 리스크(③)**: 상환 배분 기준 = 법률 검토 후 소유자. 앱은 계산·기록·감사만(법률 판단 금지).
  **배분 규칙 미확정 중엔 기록만**(`creditor_store`만·`creditor_settlement` 보류). 개인정보 370명 = 파일 분리·가림·열람 로그·
  백업 제외(§3.3·D8 §4.3·[[business-context-consignment-creditors]]).
- **R2 무인 쓰기 범위**: ① 수집 = 읽기(무인 가능·제안) · ② 계약 원장 쓰기 = 쓰기 안전 규약(dry-run→승인·무인 금지) ·
  ③ 채권 상환 기록 = **무인 절대 금지**(사람 승인·감사). 상세 = D8 §9 R2.
- **★R3 층간 역방향·순환 금지**: 흐름은 ①→②→③ 단방향 확정(§2.2). ③이 ①②를, ②가 ①을 **변경하지 않는다**(감사·되돌림은
  각 층 원장 내부). 구현 시 역의존 생기면 설계 위반. **(이 문서 신규)**
- **미결**: ①②③ 모듈 **공용 프레임 추출**(중복 측정 후·선제 추상화 금지) · 플랫폼 확대(토스쇼핑·G마켓·당근) 수집 ·
  빠른정산(셀러월렛) 수수료/조건(`[미확인]`) · 사업 꼬리표 저장 위치(분류코드 13-7 통합 여부·D8 §4.2).
