# 설계: D10 문의/CS 도메인 (고객 문의 접수·응대·상태·이력)

> 상태: **설계 초안(2026-10-05) · 구현 보류.** 소유자가 2026-10-05 app-scope 결정을 수정해 **문의(CS)만 앱에 포함**하면서 신설한 도메인(DOMAIN_DESIGN §1·§9 R5). 이 문서가 D10 기능의 SSOT다.
> 상위 설계=`docs/DOMAIN_DESIGN.md`(§1 D10·§2 D10·§5.2 원장) · 계층=`docs/ARCHITECTURE.md` · L1 계약=`docs/L1_CONTRACT.md` · 입출력=`designs/IO_DEFINITION.md`(현재 D10 칸 0=향후) · 원장 패턴 원형=`designs/LEDGER_REGISTRY.md`.
> ⚠ **전체 재작성 금지** — 기존 L0/L1 계층 위에 새 모듈로 얹고, 원장(registry) 패턴을 **재사용**한다(복붙 아님·구조 차용).
> 소유자 확정은 "(확정)", 그 외는 "(제안)"/"(미결)"로 표기한다. **구현은 소유자 지시 시 착수.**

## 0. 배경·목적

- 위탁 판매처에는 고객의 **문의(CS)**가 들어온다(상품문의·상담/톡 등). 담당자가 이를 **접수·응대·종결**하는 과정을 앱이 **기록·추적·통계**한다.
- 2026-10-02 소유자 결정은 "주문·배송·클레임·문의 = 샵마인(상용), 우리 앱은 관리·통계"였다. 2026-10-05 소유자가 이를 **수정**해 **문의(CS)만 앱에 포함**(주문 D5·배송 D6·클레임은 여전히 샵마인 범위밖). 근거=[[app-scope-no-orders-shopmine]]·DOMAIN_DESIGN §9 R5.
- **목적**: 문의가 누락·방치되지 않게 **상태(진행/완료/보류)**를 한 곳에서 보고, 응대 이력을 남겨 **지연·재발·계정별 CS량**을 측정한다. 응대 자체(고객에게 답변 전송)는 **범위 경계가 미결**(§2·§8).

## 1. 역할·범위 (경계가 이 도메인의 핵심)

### 1.1 D10이 하는 것 (문의 CS만)
- 문의 **접수**(수집 또는 수동 입력)·**분류**·**상태 관리**(접수→진행→완료/보류)·**응대 기록**·**이력 보존**·**통계**(계정별·기간별 CS량·평균 처리시간).
- 식별·연결: 문의는 **계정 + (상품 선택) + 문의자(가림)** 로 묶는다. 상품은 vid 앵커(L1 백본)로 참조.

### 1.2 D10이 하지 **않는** 것 (범위 경계·확정)
| 영역 | 담당 | 근거 |
|---|---|---|
| **주문**(발주·취소·구매고객 응대) | ⛔ 샵마인 (D5 범위밖) | DOMAIN_DESIGN §2 D5·소유자 2026-10-02 |
| **배송**(출고·송장·배송상태) | ⛔ 샵마인 (D6 범위밖) | DOMAIN_DESIGN §2 D6 |
| **클레임**(반품·교환·환불 처리) | ⛔ 샵마인 | [[app-scope-no-orders-shopmine]] |
| **내부 운영 기록**(업무일지·관리 메모) | **D8 정산/원장**(업무일지 11-4) | DOMAIN_DESIGN §2 D8·IO_DEFINITION 11-4 |

> ⚠ **업무일지(11-4)와 혼동 금지**: 업무일지는 *내부 직원의 운영 기록*(위탁 운영·관리 내용)으로 **D8** 소관이다. D10은 *외부 고객에게서 들어온 문의*만 다룬다. 둘은 상태값(진행/완료/보류)이 비슷해 보여도 **주체·대상·도메인이 다르다**(업무일지=우리 직원이 쓰는 관리 기록 / CS=고객이 보낸 문의에 대한 응대 기록).

### 1.3 애매 경계 (소유자 확인 필요 — §8 미결)
- 고객 문의가 **주문/배송/반품 관련**이면? → 성격은 CS(문의)지만 처리(실제 조치)는 샵마인. **D10은 "접수·상태·이력"만 기록하고 처리는 샵마인으로 넘긴다**(제안). 중복 응대 방지를 위해 소유자 확인 필요.

## 2. 샵마인과의 역할 분담 (중복 방지)

샵마인은 .NET WinForms + WebView2(실제 Chromium) + 로컬 SQLite로 **주문·배송·일부 CS**를 담당한다([[shopmine-architecture]]). 문의(CS)를 앱에 들이면 **샵마인과 겹칠 수 있다** → 경계를 명확히 해야 한다.

### 2.1 분담 제안 (소유자 확인 전 가설)
| 작업 | D10(우리 앱) | 샵마인 | 비고 |
|---|---|---|---|
| 쿠팡 문의 **원천 수집**(상품문의·상담) | (제안) 수동 입력 또는 세션 재사용 조회 | 샵마인이 이미 하는가? **미확인** | §4·§8 |
| 문의 **응대 전송**(고객에게 답변) | ❌ 안 함(제안) | 샵마인(또는 WING 화면) | 쓰기=고위험·§5.4 |
| 문의 **상태·이력·통계** | ✅ D10 | — | D10 고유 가치 |
| 주문/배송/반품 **처리** | ❌ | ✅ 샵마인 | 범위밖 |

### 2.2 중복 방지 원칙 (제안)
- **D10은 "응대 전송"을 하지 않는다**(초기). 답변은 담당자가 WING/샵마인에서 보내고, D10에는 *그 사실과 상태*만 기록(수동 또는 수집). → 샵마인과 쓰기가 겹치지 않음.
- 샵마인이 이미 CS를 관리한다면 **D10은 통계·추적 레이어로만** 존재하거나, 아예 수동 입력 기반 경량 트래커로 시작(§4-C). **중복 개발 방지가 2026-10-02 결정의 취지**였으므로 이 경계는 **소유자 확인 필수**(§8 Q1).

## 3. 데이터 모델 (append 원장 + 상태 replay — registry 패턴 재사용)

D8 원장(registry)과 **같은 철학**: 지우지 않고 쌓고, 상태는 이력에서 계산한다(DOMAIN_DESIGN §5.2). 단 **원장 대상이 다르다**(계정×상품이 아니라 *문의 건*) → `registry_*`를 직접 쓰지 않고 **별도 모듈이 같은 구조를 차용**한다.

### 3.1 엔터티
- **문의(Inquiry)**: 접수 1건. 안정 키 = `문의ID`(앱 발번·예 `Q-0000`). 속성: 계정ID·상품(vid·선택)·채널(상품문의/상담/기타)·문의자(가림)·접수일시·제목/요약·분류.
- **응대/상태 이벤트(Event)**: 그 문의에 대한 **추가만** 되는 이력 줄(답변·상태변경·보류사유·종결). registry의 `HistRow`에 해당.
- **현재 상태**: 이벤트를 시간순 replay해 **접수/진행/보류/완료**를 계산(registry `_replay_status`와 같은 방식). 저장 열은 렌더 결과.

### 3.2 상태 모델 (제안)
```
접수(RECEIVED) → 진행(IN_PROGRESS) → 완료(DONE)
                      ↘ 보류(HOLD) ↗   (보류는 사유 필수·재개 가능)
```
- 상태는 **이벤트 kind로 결정**: `접수`·`진행`·`보류`·`재개`·`완료`·`재개방`(완료 후 재문의). registry의 OPENERS/STOP 구조와 평행.
- **SLA 추적(제안)**: `접수→완료` 경과시간·`N일 넘은 진행`은 업무일지(11-4)의 "7일 넘은 진행 표시"와 같은 규칙 재사용 가능.

### 3.3 민감정보 처리 (확정 방향 — R2②와 일치)
- 문의자 **이름·연락처·주소**는 **개인정보** → 화면·결과·로그 **원문 금지·가림**(마스킹), 권한자만 원문. 채권자 파일(IO_DEFINITION 12-x·R2②)과 **같은 규칙**.
- 저장 위치: R2(구글시트로 시작)를 따르되, **개인정보 포함 시 별도 파일 분리 + 권한 제한**을 검토(채권자 파일 선례). 앱 로그에는 ID·상태만, 연락처 값 금지.

### 3.4 무결성 (registry 재사용)
- 이벤트 **번호 연속**·**추가만**(정정은 반대 이벤트)·**이력 전부 되돌리면 빈 원장** — registry_history `check_integrity`와 동형. 실행마다 로컬 백업(개인정보 포함 시 백업 정책은 §8).

## 4. 쿠팡 문의 수집 경로 조사 (⚠ WING API/화면 경로 **미확인** — 조사·제안)

> 실측 근거: `src/` 전체에 문의/CS 수집 코드 **없음**(grep 확인). WING의 상품문의·고객상담 화면·API 경로는 이 프로젝트 자료에 **문서화되어 있지 않다**([[coupang-official-reference]]에도 CS 라우트 없음). 아래는 **가능 방식 제안**이며 실제 경로는 사무실 라이브 조사가 필요하다.

### 4-A. 세션 재사용 데이터 조회 (collector 패턴 — 중위험)
- `WingBrowser` 로그인 세션의 `wb.page`에서 same-origin fetch(`_POST_JSON_JS`/`_GET_JSON_JS` + `x-xsrf-token`)로 문의 목록 API 직접 조회(L1 조회 프리미티브 패턴·L1_CONTRACT §1).
- **전제**: WING에 문의 조회 엔드포인트가 존재하고 그 세션으로 접근 가능해야 함 → **엔드포인트·응답 스키마 미확인**. 사무실 라이브로 DevTools 네트워크 관찰 필요.
- 리스크: Akamai(로그인 세션은 통과해 왔음·판매데이터 선례)·위탁계정 과도 호출. **쓰기(답변 전송)는 절대 금지**(§5.4·§2.2).

### 4-B. 반자동 화면 읽기 (rank 반자동 패턴 — 저~중위험)
- 보이는 WING 창에서 담당자가 문의 화면을 열면 앱이 **DOM만 읽어** 목록을 긁음(detail_images의 CDP attach 또는 rank 반자동과 유사). 네비/타이핑 최소.
- 장점: API 미확인이어도 가능·사람이 띄운 세션. 단점: 화면 구조 의존·정밀도(스코핑 필요·detail_images 선례).

### 4-C. 수동 입력 (무수집·최저위험 — **초기 권장**)
- 담당자가 문의를 화면(09-x)에 **직접 입력**(수집 코드 0). 쿠팡/WING·Akamai·개인정보 자동수집 리스크 전무. 샵마인과도 안 겹침.
- **제안: 4-C로 시작**해 트래커·통계 가치를 먼저 검증하고(§9 로드맵 1단계), 수집(4-A/4-B)은 경로 확인·소유자 승인 후 도입. R2(구글시트 시작)·"조회만으로 가치 검증 후 쓰기"(R1)와 정합.

## 5. 화면 매핑 (신규 메뉴 — IO_DEFINITION 체계와 정합)

IO_DEFINITION 메뉴 체계: 01 상품·03 재고·04 정산/매출·06 마케팅·07 키워드·08 판매처/계정/수집/변경이력·11 계약/업무일지·12 채권자·13 설정. **09·10은 미사용** → D10을 **09 문의/CS**로 (제안, task 힌트 "09-x" 수용).

| 메뉴 ID(제안) | 화면 | 역할 |
|---|---|---|
| **09-1 문의 목록** | 접수된 문의 리스트(상태·계정·상품·채널 필터·검색) | 전체 조망·방치 건 하이라이트 |
| **09-2 문의 상세·응대** | 한 건의 이력·상태변경·응대 기록 추가 | append 이벤트 입력(사람이 쓰는 칸) |
| **09-3 문의 접수** | 수동 입력(4-C) 또는 수집 결과 확인 | 초기 진입점 |
| **09-4 CS 통계** | 계정별·기간별 건수·처리시간·보류율(D9 통계로 융합 가능) | 측정 |

- IO_DEFINITION §1 표에 D10 행 추가(현재 "0=향후")는 **통합 세션 소관**(IO_DEFINITION은 H_ui/통합 공유 문서) — 이 설계가 칸을 제안하면 통합이 반영.
- 홈 시안(3장: 홈·상품관리·매출정산)엔 문의가 없음 → **디자인 반영도 통합/H_ui 소관**(여기선 메뉴 ID만 제안).

## 6. 신규 모듈 제안 (단일책임 · CC≤15 · ≤600줄 · 레인 배치)

registry 패밀리의 **모듈 분할 방식을 그대로 차용**(model/core/gsheet 3분할). D8 원장과 **대상이 달라 별도 파일**이되 공용 패턴은 재사용.

| 모듈(제안) | 책임 | 비고 |
|---|---|---|
| `cs_model.py` | 시트·열·채널·상태·이벤트 kind 상수, 값 정규화(`canon` 재사용 검토), 문의/이벤트 데이터클래스 | registry_model 평행 |
| `cs_store.py` | `CSLog`(문의 줄 + 이벤트), 상태 replay(`_replay_status` 평행), 접수/진행/보류/완료/통계 계산 | registry_core+history 평행 |
| `cs_gsheet.py` | 구글시트 입출력(시트 생성·서식·읽기·append·백업)·개인정보 가림·권한 | registry_gsheet 평행·L0 `gsheet_api` 재사용 |
| `ui/cs_panel_qt.py`(제안) | 09-x 탭(목록·상세·접수·통계) | H_ui 레인 |
| (수집 도입 시) `cs_collect.py` | 4-A/4-B 수집(세션 재사용/반자동) — **2단계 이후·경로 확인 후** | L1 조회 프리미티브 호출 |

- **레인**: D10은 PARALLEL_DEV 레인에 신규 추가(제안 "I CS" 또는 기존 "E 원장/정산"이 흡수) — 비겹침 파일집합(`cs_*`·`ui/cs_panel_qt`)이라 병합 깨끗. config/pipeline/browser는 공유=통합 세션 경유.
- **의존 방향**: D10(L2)은 L0(browser·credstore·gsheet_api)·L1(가능하면 백본)로만 의존. **다른 도메인 직접 import 금지**(ARCHITECTURE §2). 상품명/vid는 workbook·백본에서 키로 참조.

## 7. 공개 인터페이스 계약 초안 (구현 착수 시 L1_CONTRACT/핀 등재)

> registry 계약(L1_CONTRACT §7) 양식을 따른 **초안**. 시그니처는 구현 전이라 (제안)이며, 확정 시 `pin_*`에 등재.

```
# cs_store (문의 원장·상태 계산) — 호출처: ui(H_ui)·(수집 도입 시) pipeline
cs_store.parse_log(rows)                         -> CSLog        # 시트 → 자료구조
cs_store.open_inquiry(log, *, account_id, product=None, channel, asker, summary, now) -> Inquiry  # 접수(append)
cs_store.add_event(log, inquiry_id, *, kind, note="", now)       -> Event   # 진행/보류/재개/완료(append)
cs_store.status_of(log, inquiry_id)              -> str          # replay 결과(접수/진행/보류/완료)
cs_store.open_inquiries(log, *, account_id=None) -> list[Inquiry]            # 미완료 조망
cs_store.stats(log, start, end)                  -> dict         # 건수·평균 처리시간·보류율
cs_store.check_integrity(log)                    -> None         # 번호 연속·replay 일치

# cs_gsheet (구글시트 IO) — 호출처: ui·cs_store
cs_gsheet.run_sync(client, log, *, now, log_fn=None, dry_run=False, backup_dir=..., lock_path=...)
cs_gsheet.append_events(client, events, *, dry_run=False)        -> int      # 이력 append(가림 적용)
```
- 개인정보 가림은 **쓰기 직전**(gsheet)과 **조회 반환 시**(store) 양쪽에서 마스킹(권한 플래그로 원문 허용).
- 원장 동시 쓰기 잠금(`registry_lock` 재사용)·RAW 쓰기(연락처 서식 보존)는 registry 선례 그대로.

## 9. 로드맵 단계 · 게이트/핀 계획 (오프라인 검증)
